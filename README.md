# Replication package

Code for the ARP-spoofing-detection / SmartNIC-deployability pipeline used
in the paper: data cleaning → EDA → train-only feature engineering and
model training under SmartNIC hardware constraints (S1-S4 scenarios) →
integer quantization → multi-seed stability check → P4/BMv2
hardware-fidelity validation for the two deployable scenarios (S3, S4).

No data or trained models are included here -- only the code. The dataset
(CICIoT2023) cannot be redistributed under its usage terms, and the
trained models are multi-gigabyte binaries that don't belong in a git
repo; both are regenerated by running the pipeline.

## Pipeline

| Script | Stage | Output |
|---|---|---|
| `01_data_cleaning/01_data_cleaning.py` | Load raw CICFlowMeter CSVs, apply domain-grounded cleaning fixes, validate against impossible values, remove outliers/duplicates | `data/final_dataset.csv` |
| `02_eda/02_eda.py` | Purely descriptive EDA on the full cleaned dataset: distribution shape, class balance, unsupervised structure (PCA/K-Means/t-SNE). No label-dependent feature decisions -- those require a train split, done in stage 3 | `plots/*.png` |
| `03_modeling/03_modeling.py` | **Part 1/2**: train/val/test split; train-only statistical feature reduction; SmartNIC-observable feature subsetting; engineered-feature screening; trains 4 scenarios (S1 Gateway Baseline, S2 SmartNIC Observable, S3 SmartNIC Deployable, S4 SmartNIC Deployable + FE); derives and verifies integer quantization for S2-S4; threshold analysis; feature importance; lift/cumulative-gains analysis. **Part 3**: repeats preprocessing and final-fit-only evaluation under four further random seeds (hyperparameters frozen from Part 2's search, not re-searched), to characterize how much the reported metrics depend on the particular split drawn | `modeling/{results,models,plots}/*` |
| `04_p4_validation/04_generate_p4.py` | Extracts the fitted, integer-quantized S3 and S4 Decision Trees and generates, for each, a P4_16 program plus a Scapy test harness that validate the tree's match-action logic against BMv2; finishes with a static resource-footprint summary (program size, tables/actions, header width, registers) read directly from both generated programs | `p4_validation/*`, `modeling/results/p4_resource_summary.json` |

Each stage reads the previous stage's checkpoint and writes its own; run
them in order. See `outputs/README.md` for exactly what every generated
file contains.

## Reproducibility

- **Random seed**: `random_state=42` is the primary seed, fixed everywhere
  a `scikit-learn` call accepts one throughout Parts 1-2 (the train/val/test
  split, every model, every stratified sample) -- set once and never
  overridden. Part 3 additionally runs the same pipeline under four more
  seeds (7, 123, 2024, 99) to report how stable the headline metrics are
  to that choice, reusing Part 2's already-found hyperparameters rather
  than re-searching per seed.
- **Library versions**: pinned exactly (not `>=`) in `requirements.txt`.
  `scikit-learn`'s CART split selection and tie-breaking are
  version-sensitive enough to shift the exact tree learned -- install the
  pinned versions, not just "recent" ones, if you need the same tree
  structure reported in the paper.
- **Python**: tested with 3.14.2.

## Running the pipeline

From the repo root, with `data/{Benign_Final,MITM-ArpSpoofing}/` already
in place (see `data/README.md`):

```bash
python 01_data_cleaning/01_data_cleaning.py   # -> data/final_dataset.csv
python 02_eda/02_eda.py                       # -> plots/
python 03_modeling/03_modeling.py             # -> modeling/{results,models,plots}/
python 04_p4_validation/04_generate_p4.py     # -> p4_validation/
```

`03_modeling.py` is the expensive stage (full hyperparameter search across
4 scenarios, plus integer retraining, plus the 4-seed stability check in
Part 3); the others run in minutes. Part 3 itself is fast relative to
Parts 1-2, since it reuses their cached hyperparameters instead of
searching again.

Every script resolves its own paths relative to its own file location
(`repo_root = parent of the folder containing the script`), so the repo
works regardless of where it's cloned -- no paths need editing.

## P4 hardware-fidelity validation

`04_generate_p4.py` only generates the P4 programs and test harnesses; it
doesn't compile or run them -- that needs `p4c` and BMv2 (`simple_switch`)
on a Linux environment (a VM is the simplest route). Both S3 (no feature
engineering; the scenario recommended as the operational default) and S4
(adds the two engineered features its tree actually splits on) are
validated the same way, each against its own ethertype pair so their
traffic can't be cross-confused on the same VM. Full setup, exact tool
versions, and the actual measured results --

| Scenario | Match | Mismatch | Timeout |
|---|---|---|---|
| S3 | 205,231 / 210,863 (97.33%) | 0 (0.00%) | 5,632 (2.67%) |
| S4 | 209,093 / 210,863 (99.16%) | 0 (0.00%) | 1,770 (0.84%) |

-- are in `04_p4_validation/vm_setup.md`. Zero mismatches for both
scenarios confirms the P4 encoding is faithful to the Python model;
timeouts are VM-load artifacts (see `vm_setup.md` for the diagnostic
checks), not classification errors.
